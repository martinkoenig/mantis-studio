Status: L0, L1 and L2 FINAL ACCEPTED.
L3 implemented, acceptance pending; L4–L8 remain planned. No laser hardware acceptance is claimed.

Normative decisions: [ADR-040](../adr/040-projected-light-programs-and-safe-state-ownership.md),
[ADR-041](../adr/041-laser-observations-and-acquisition-evidence.md),
[ADR-042](../adr/042-additive-projected-light-plugin-contract.md) and
[ADR-043](../adr/043-versioned-projected-light-recording-and-replay.md).
The frozen [Architecture v1](../../MANTIS_STUDIO_ARCHITECTURE.md) remains authoritative.

### L3 implementation status

The Qt-free daemon-owned run supervisor, finite lossless publication queue, bounded
coverage/correlation state and priority abort path are implemented. See the
[sequencer contract](projected-light-sequencer.md) for lifecycle, evidence policy,
deadlines, resource admission and software-only validation. L3 acceptance is pending.
Recording, protobuf and production projected-light hardware remain deferred.

### L2 implementation status (FINAL ACCEPTED)

The additive native contract, SDK, device abstraction, explicit runtime factory,
bounded semantic views and test-only DSO are implemented. See the concrete
[projected-light plugin API](projected-light-plugin-api.md) for lifecycle, deadlines,
ownership, abort concurrency and compatibility rules. Public L2 ABI layouts and
values are frozen with portable contract snapshots. No recorder codec, protobuf API
or X1 projected-light hardware is added.

### L1 implementation status (FINAL ACCEPTED)

[projected_light.hpp](../../src/data/include/mantis/projected_light.hpp) and
[projected_light.cpp](../../src/data/projected_light.cpp) implement schema-1
AcquisitionProgram, TriggerEvent, AcquisitionEvidence, AcquisitionBundle and
LaserObservation as Qt-free values with deterministic `Result<void>` validators.
The five exact semantic identities are in `mantis-schema`. Stable typed keys,
three-alternative evidence (established/unknown/unavailable), separate command /
acknowledgement / observation / exposure-effective groups, evidence scopes,
generation-scoped clocks and exact camera/rig references stay below device APIs.
Content references use base IDs/hashes; no artifact-api dependency is introduced.
Bundles carry one evidence value, zero or one actual immutable `Published` FrameSet,
and bounded trigger values. FrameSet/source-frame keys remain in the evidence;
attached packets retain unchanged image-only invariants and shared pixel buffers.
They do not extend `data::Packet` or implement a codec. Resolved calibration content
requires the matching kind/schema/revision and an established hash; unresolved
content stays explicitly unknown/unavailable. Real/synthetic observations require
an established run identity; imported observations can explicitly lack one.
Known emitter/line unknown-quality bits must agree with present validity masks;
future quality bits remain unchanged.

L1 checks finite positive run/step/continuous-ON caps, nonnegative settling and
checked step-count expansion. Deadlines are independent caps, not prescribed
elapsed durations: summing all maximum step deadlines is not a required run time.
The single ON cap spans steps/repetitions; elapsed-time enforcement, capability
feasibility, reservations and program-specific evidence satisfaction belong to L3.
Established effective state requires full coverage of the established exposure in
the same clock generation; mappings are retained explicitly, never inferred from
host time. Contradictory reported states remain separate facts. Required states, acknowledgement
results, capture/evidence choices and dispositions reject omission rather than
defaulting to OFF/success. Pattern references can remain known with unknown lines;
valid dictionary attribution is a producer claim, with physical emission evidence
retained separately.

In addition to the frozen 256 declared steps / 1,000,000 executed steps / 64 bundle
members, L1 uses implementation sanity limits: 64 participants (at most 16 cameras),
4096 entries per generic semantic table/dictionary, 256 bytes per stable ID,
1024 bytes per string, 128 observation attributes, 1,000,000 samples and 128 MiB of
observation attribute buffers. Per-frame/per-emitter tables inherit the participant
limits. These are memory/resource bounds, not hardware or physical safety limits.
Executors may advertise smaller limits. Unknown flags/valid namespaced extensions
are retained; mask=0 values use L0's finite zero placeholders and establish no value.
Successful zero detections have N=0 and no attributes; extractor failure and
unavailability have distinct dispositions.

Focused tests are in [projected_light.cpp](../../tests/unit/projected_light.cpp).
L1 left the plugin ABI unchanged. L2 adds optional queried interfaces; RawCapture
codecs, protocol, X1 hardware and extraction remain unchanged.

## 1. Goal, scope and inherited contracts

Make projected-light control, timing, camera association and evidence deterministic
where the executor can establish them, without interpreting a software request as
a physical measurement. Define the typed `LaserObservation` boundary that future
image algorithms and downstream reconstruction can share.

| Release | Required boundary |
| --- | --- |
| v0.4 | Generic emitter semantics, default OFF, bounded validated acquisition programs, deterministic sequencing decisions, explicit trigger/exposure evidence, exact emitter/step provenance, persistence/replay, compact daemon controls and LaserObservation schema-1 infrastructure, synthetic/test producers |
| v0.5 | Production L1 line extraction, L7 multi-line extraction, subpixel localization, seven-line identity/disambiguation, laser-plane/projector geometric calibration, triangulation and metric 3D observations |
| v0.6+ | Tracking, registration, fusion, meshing, texture and metrology under the [roadmap](../../ROADMAP.md) |

[ADR-031](../adr/031-x1-remote-observation-boundary.md) specifies the **final
deployment partition**, not the release in which an extractor first exists.
v0.4 supplies its acquisition and typed observation infrastructure; v0.5 supplies
the real image-to-observation algorithms, source-proximal on Q6A by default.
No real extraction, XYZ reconstruction, licensing, full remote transport or
worker-pool implementation is implicit in v0.4 or L0.

Inherited requirements include daemon ownership (ADRs 001–002), queried C ABI
(003–006), separate control/data planes (007–008), typed DAG and immutable
publication (013–014), explicit clocks (016), ARM64 Tier 1 (017), recoverable raw
capture/replay (018–019), generic capabilities (020–026), exact camera/rig
calibration binding (030), X1/distributed authority (031–032), bounded reliability
(033), evidence-scoped physical acceptance (037), extensible observations (038)
and bridged hardware (039). See the [ADR index](../adr/README.md).

## 2. Terminology and identity

| Term | Frozen meaning |
| --- | --- |
| Emitter / projector | A controllable projected-light component; projector describes its pattern, not a scanner class |
| Program | Immutable versioned finite description of requested light state and capture/trigger intent |
| Run / generation | One daemon-owned execution; new identity on restart/reset/reconnect; never splice stale events into a new run |
| Step instance | `(run_id, repetition_index, step_index)`; declared step index is not a camera counter |
| Commanded | Software issued a request, retaining command ID, target, requested value and dispatch time |
| Acknowledged | Named controller accepted/rejected/completed the request, with the acknowledgement stage explicitly stated |
| Observed | A named evidence source reported a value/event, with time, clock and method |
| Effective | State established for a specified exposure interval by evidence whose scope covers that interval |
| Unknown / unavailable | Unknown is an unresolved value; unavailable means the source cannot provide that evidence. Neither means OFF, zero, success or synchronized |
| DARK | Requested OFF for every participating emitter; it does not certify optical darkness |
| LaserObservation | Image/sample-space measurement candidates, with source and illumination provenance; no triangulated XYZ |

Identities include capture/run generation, stable component and stream IDs and
native frame counters. Counter reset/wrap semantics must be declared by the source;
unexplained reversal, duplication or generation mixing fails. Labels such as LEFT,
L1 and L7 are presentation/configuration roles. Existing X1 camera role values
`left`/`right` stay exact; IDs never derive from transient `/dev/video` numbers.

## 3. Capability-based Device Graph

The X1 reference graph is a logical parent with components:

```text
X1 acquisition parent (existing stable logical ID)
  camera left   — image-stream; optional exposure/trigger capabilities
  camera right  — image-stream; optional exposure/trigger capabilities
  emitter L1    — power-control; pattern descriptor
  emitter L7    — power-control; pattern descriptor
  timing controller — hardware-trigger / program executor, when accessible
```

This is a reference topology, not a required number/type of cameras or emitters.
One controller may operate several emitters/cameras. Ownership and control edges
are explicit component-ID references in a versioned descriptor, separate from
parent containment; duplicate control authority is rejected. A controller can be
an integrated parent capability when no separately discoverable component exists.
Expose only accessible functionality; physically present but inaccessible hardware
cannot advertise control/readback capabilities. L7 establishes actual X1 component
identities without changing its existing camera-derived parent or camera IDs.

| Identifier | Meaning / version convention |
| --- | --- |
| `org.mantis.camera.image-stream.v1`, `org.mantis.camera.frameset-stream.v1` | Existing discoverable capabilities |
| `org.mantis.camera.exposure-control.v1`, `org.mantis.camera.gain-control.v1` | Architecture-v1 capability names; advertise only supported controls |
| `org.mantis.emitter.power-control.v1` | Generic commanded OFF/ON enable control; no calibrated optical power promise |
| `org.mantis.emitter.state-feedback.v1` | Optional feedback with explicit electrical/optical scope and temporal validity |
| `org.mantis.trigger.hardware.v1` | Actual accessible hardware-trigger function; descriptor names endpoints, pulse/timing limits and association evidence |
| `org.mantis.acquisition.projected-light.v1` | Parent supports validated projected-light programs and evidence-bearing acquisition |
| `org.mantis.projected-light.v1` | New queried native interface implementing that capability, defined by L2 |

Capabilities and interface names are lower-case namespaced identifiers with a
`.vN` suffix. Semantic packet/artifact names use `org.mantis.TypeName` plus an
independent integer schema version. Attribute names are lower-case namespaced
fields, independently described by scalar/shape/stride/unit. Community extensions
use their own namespace (ADRs 038–039); product names belong in descriptors/plugins.
L0 reserves these identifiers. L1 implements the semantic schema identities;
capability/interface implementations remain L2.

Descriptors declare supported states, pattern ID/revision and optional known line
IDs, control relationships, supported execution/timing modes, evidence methods,
interlocks/watchdogs and hard resource limits. A line-count hint is not measured
line identity or laser geometry. Camera calibration compatibility checks only
explicitly participating image components, retaining exact physical identity,
role and dimensions. Core contains no L1/L7 or X1 product-name conditionals.

## 4. Projected-light acquisition program schema 1

Reserve `org.mantis.AcquisitionProgram`, schema 1. It is configuration, not a
cyclic pipeline recipe. Persistence supplies immutable artifact ID/hash; execution
snapshots the program, capabilities, binding and implementation versions.

| Program property | Requirement |
| --- | --- |
| Participants | Explicit stable emitter/camera/controller IDs and stream IDs; no implicit global active scanner |
| Steps | Ordered nonempty list with unique step labels and stable indices |
| Repetition | Explicit positive finite count; no infinite loop, recursion, branches or automatic retry in v1 |
| Light intent | Complete OFF/ON state vector for all participating emitters in every step; no inherited unspecified ON state |
| Timing | Nonnegative minimum settle interval, positive maximum step duration and ON-duration bound, explicit units/clock semantics |
| Capture intent | Either no capture or one requested FrameSet from an explicit camera set; explicit free-running or hardware-trigger mode |
| Trigger intent | Optional target controller/endpoints and logical request ID; hardware pulse realization comes from validated executor configuration |
| Evidence requirement | Explicit commanded-only, controller-acknowledged or exposure-effective requirement; no fallback between them |
| Run bounds | Maximum run duration, executed steps, command/event counts, bytes and in-flight capture intents; checked arithmetic |
| Terminal policy | Mandatory inhibit-future-triggers and request-all-OFF on completion, stop or fault |

v1 permits at most **256 declared steps**, with at most **1,000,000 executed step
instances** after repetition; implementations may impose smaller advertised limits.
Every run also has an explicit finite duration. These are software resource ceilings,
not laser-safety or hardware timing thresholds. Strings, descriptors, parameters and
evidence counts/bytes must fit the negotiated limits before arming.
An OFF-only program is valid. Simultaneous ON emitters require explicit executor
support; they are never assumed safe or supported. A representative X1 configuration
may request `DARK -> L1 -> DARK -> L7` with a caller-selected finite repeat count.

Validation resolves capabilities and ownership, timing/rate/storage feasibility,
state combinations, evidence support, calibration compatibility and all resource
bounds before enabling anything. Missing controller/evidence capability returns
incompatible/unsupported; invalid bounds return invalid argument; reservation
conflicts return busy. No unsupported program runs under a hidden software fallback.
Programming/configuration changes require a new run; live mutation is excluded.
ON-duration accounting spans consecutive steps/repetitions that leave an emitter
ON; a new step does not reset that bound. Settling is a requested minimum between
the light transition and exposure start. Its realized interval is established only
by the executor's declared timing/evidence contract; a host sleep after dispatch
does not establish when hardware settled. A hardware-trigger capture intent requires
a trigger request; a free-running intent must not synthesize a hardware trigger ID.

| Layer | Responsibility |
| --- | --- |
| Semantic program | Desired states, order, timing constraints, capture mode, evidence requirements and finite limits |
| Daemon sequencer | Validate/reserve, assign run/command identities, advance causal state, collect immutable evidence, enforce deadlines and fail explicitly |
| Device plugin | Discover/map components, validate actual modes, own hardware handles, translate executor requests, preserve native metadata |
| Hardware executor | Realize timing/state/trigger operations locally with advertised resolution, capacity, cancellation/inhibit and evidence guarantees |
| Diagnostics | Requested versus realized timing, lateness, readback, rejected commands, queue occupancy, fault and cleanup outcomes |

Determinism means the same validated program and ordered executor evidence produce
the same semantic decisions and correlations. It does not guarantee identical
wall-clock execution, sensor pixels or hard real-time Linux scheduling. Strict
timing belongs in a capable firmware/dedicated executor (Architecture v1 §18).
Late deadlines fail; missed steps are not silently compressed or skipped.
Free-running frames may be associated by a declared software rule while effective
illumination remains unknown. A known-light measurement mode requires established
exposure coverage; timestamp proximity alone cannot supply it.

## 5. State, ownership and failure model

One daemon run exclusively owns the participating control resources. Clients
submit/stop programs and observe state. Pipeline nodes cannot directly toggle
emitters; feedback produces bounded control-plane requests for a future run.

Run states are VALIDATING, READY, RUNNING, STOPPING and terminal COMPLETED,
CANCELLED or FAILED. READY means reservations/configuration and required startup
evidence passed, not a certified physical safe state. Faults latch FAILED; restart
requires a new run and preflight. Artifact OPEN/FINALIZING/FINALIZED/RECOVERABLE
is a separate storage state; a finalized recovered prefix is not a completed run.
Validation/preparation failure transitions directly to FAILED without ON work;
successful preparation reaches READY, start reaches RUNNING, and all completion,
stop, cancellation or runtime-fault paths pass through STOPPING. Fault takes
precedence over cancellation, which takes precedence over normal completion.

Default requested emitter state is **OFF**, including start/reset/teardown.
Preflight requests OFF and records available acknowledgement/readback before ON.
State is tracked per emitter as commanded state, acknowledgement stage/result,
observed state/method/interval and exposure-effective state. Evidence of an enable
pin being high establishes an electrical signal only; optical emission requires
appropriate sensing. A point readback cannot establish state over a whole exposure.
Each observed/effective value names its scope (controller register, electrical
enable or optical emission); a consumer requiring optical evidence must reject
electrical-only evidence. Interval guarantees based on a validated executor remain
identified as such rather than relabelled as direct optical sensing.
Contradictory evidence is retained and fails a requirement that depended on it.

The common bounded abort path first latches the reason, inhibits new trigger/ON
work, invalidates queued commands for that run, requests all participating emitters
OFF through a priority path, and cancels/drains already accepted hardware work
according to the executor contract. Then it resolves bounded in-flight observations,
records terminal evidence, drains healthy recorder work and releases resources.
OFF has a separate reserved capacity and may not wait behind the recorder or a
full ordinary command queue. Required acknowledgement/readback timeouts and cleanup
errors remain separate from the initiating failure. No automatic re-enable occurs.
Executor cancellation must fence already submitted ON/trigger work, so a late
command cannot re-enable an emitter after OFF. If hardware cannot establish that
fence, retain the unresolved pending-work outcome and rely on the independent
hardware mechanism; do not report a confirmed stopped hardware state.

| Event | Required outcome |
| --- | --- |
| Finite program completion / normal stop | Abort path without fault; record OFF request/outcome, drain already published data, finalize only validated records; cleanup failure makes run FAILED |
| Explicit cancellation | Same OFF/inhibit path; CANCELLED unless a fault/cleanup failure takes precedence; no loss concealed as successful completion |
| Step, camera, acknowledgement or trigger timeout | FAILED, OFF/inhibit immediately; unresolved exposure/command outcome remains unknown |
| Camera failure/disconnect | FAILED for affected run; no substitute frames or timestamp re-pairing to conceal missing triggered observations |
| Trigger-controller failure | FAILED; best-effort inhibit/OFF via any still-available control path; trigger delivery remains unknown unless evidenced |
| Emitter-controller failure | FAILED; request OFF where possible; unavailable physical OFF is explicit, never successful confirmation |
| Sequencer failure | Supervising runtime/plugin cleanup requests inhibit/OFF within its bounds; process death relies on independent hardware mechanisms |
| Recorder saturation, disk full or failure | FAILED and OFF/inhibit before writer drain; keep valid prefix RECOVERABLE and root cause; evidence persistence failure remains explicit |
| Daemon shutdown | Stop all owned projected-light runs before plugin unload; bounded cleanup, record unresolved state; abrupt kill cannot execute software cleanup |
| Plugin teardown/crash | Inhibit/OFF before orderly handle destruction; retain instance/table/buffer lifetimes until calls complete; crash outcome uses independent hardware safety |
| Studio/control-client disconnect | Finite autonomous run continues under daemon ownership; no client heartbeat needed to maintain safety; explicit stop/cancel remains a separate command |
| Hardware/bridge transport disconnect | Executor failure, invalidate generation and run OFF/inhibit path; hardware-local watchdog/interlock must handle loss of host control |
| Required downstream consumer disconnect/backpressure | Continue only if prevalidated finite local recording/buffering can preserve authoritative data; otherwise FAILED and OFF; optional preview loss is counted |

Software OFF is a request, **not a physical safety guarantee**. Independent
interlocks, fail-OFF circuits and local watchdogs must work even when Linux,
`mantisd`, plugin threads or transport fail. Their existence and tested behavior
are hardware facts required before real laser operation in L7/L8. Firmware may
reject ON despite daemon intent (ADR-039). L0 selects no controller and makes no
laser-safety, functional-safety or certification claim.

## 6. Trigger, exposure and synchronization evidence

Reserve `org.mantis.TriggerEvent`, schema 1. A requested trigger, a controller
acknowledgement and an observed edge are distinct events with distinct evidence.

| Field group | Required meaning |
| --- | --- |
| Identity | Run/generation, event sequence, controller/source ID, step instance, command/request ID and optional native trigger ID |
| Kind / result | requested, acknowledged (accepted/completed/rejected), observed, timed-out or cancelled; method/source and explicit unavailable fields |
| Time | Device timestamp/clock and host receive/dispatch time with their clock identity; optional observation uncertainty and clock-mapping reference |
| Targets | Explicit intended endpoint IDs; actual delivered/observed endpoints only where supported |
| Exposure association | Camera stream/native sequence, association method and evidence reference; requested association is separate from established association |

Trigger identity is scoped to controller generation, not a bare counter. A
software request ID is never copied into the hardware trigger field as proof of
delivery. A hardware acknowledgement means only its declared stage: accepting a
command does not establish an output edge or an exposure. SyncGroup identifies a
declared group and correlated trigger/association; SyncQuality states the evidence
class. Hardware quality requires supported evidence linking the images to the
same actual physical trigger, not equal native counters or operator configuration.

Exposure evidence records start/end or integration interval, sensor clock, timestamp
semantics (such as start-of-exposure versus driver delivery), method and uncertainty
where known. Requested exposure, startup driver control readback, per-exposure
measurement and host receive time are distinct. If unavailable, no start/end,
duration or skew is calculated as though measured. Clock comparison requires the
same known domain/generation or a retained versioned mapping with uncertainty.

Emitter effective-state evidence references the exact source frame and covers its
whole exposure interval, including settle/hold constraints. Partial coverage or
an unknown exposure interval yields unknown effective state. Hardware scheduling
can provide interval guarantees only under its declared, physically validated
executor contract. Same trigger association does not establish optical
simultaneity. Optical exposure skew needs independent physical measurement,
instrument/method and uncertainty; equal counters/timestamps never establish it.

## 7. Acquisition evidence and the canonical recording unit

Reserve `org.mantis.AcquisitionBundle` and `org.mantis.AcquisitionEvidence`, both
schema 1. The outer bundle is the authoritative immutable acquisition publication
unit for projected-light runs; FrameSet schema 1 remains the image association
unit within it. This supports native, composite and future bridged devices.

A bundle contains its capture/run identity and strictly increasing bundle sequence,
one AcquisitionEvidence packet, zero or one unchanged FrameSet and zero or more
TriggerEvents. Members have explicit typed roles and stable identities; no arbitrary
recursive packet graph is allowed. At most 64 members are allowed, including the
evidence and FrameSet. FrameSet still contains at most 16 images. Empty image sets
are never fabricated: initialization, control-only steps, timeouts and termination
can publish evidence-only bundles.
The bundle header timestamp is runtime monotonic publication time with its clock
domain/generation, not an exposure timestamp; host receive/pacing time is explicitly
identified. Members retain original native timestamps, counters, sync and calibration.
The runtime assigns recorded event ordinals preserving known causal dependencies;
these ordinals do not assert physical order between unrelated clock domains.

AcquisitionEvidence has a versioned typed descriptor/table representation for:

- program artifact ID/hash, run/generation, step instance and event order;
- participating components and configuration/executor/plugin versions;
- per-emitter command identity/state/dispatch time, acknowledgement stage/result,
  observed state/method/time validity and per-camera exposure-effective state;
- source FrameSet and camera/native frame keys, capture/association method,
  trigger references, exposure intervals and clock mappings;
- exact camera/rig calibration references and original source-device reference;
- disposition (startup, captured, control-only, completed, failed, stopped, cancelled), typed
  reasons, unresolved requests and loss/exclusion accounting.

Use bounded descriptors and typed arrays/validity masks where entries repeat;
human-readable metadata is explanatory only. Unknown and unavailable values are
encoded explicitly, never as zero counters or magic successful state. The semantic
field groups above are mandatory even if their physical values are unavailable.
AcquisitionEvidence encoding must round-trip them without string parsing heuristics.

Before triggering, reserve room for the resulting bundle and worst-case evidence.
Every executed control-only step also yields evidence. If a bundle cannot fit,
preflight rejects it or the run fails before further triggering; never omit evidence
to fit a record. Events within a bundle have a total source-local event order;
cross-clock order is not inferred from sorting timestamps. Events received after
publication produce a later evidence-only bundle referencing the original frame,
never mutation of the prior bundle. Consumers requiring complete effective-state
evidence wait under a finite deadline/window or report it unknown/fail by policy.

Program intent, emitted commands, executor acceptance, trigger observations,
received frames, published bundles and committed records are accounted separately.
An unobserved exposure count can remain unknown. Recorder LOSSLESS covers published
authoritative bundles, not every possible physical exposure. Failed pending
requests and unmatched frames are retained as evidence, without invented images.

## 8. LaserObservation semantic schema 1

Reserve `org.mantis.LaserObservation`, schema 1, independent of application/ABI/
container versions. It is an immutable bulk packet scoped to **one source image**
and a producer stream. Multiple cameras publish separate packets with correlation
references; vector position does not establish stereo correspondence.

| Context | Schema-1 requirement |
| --- | --- |
| Observation key | Capture/run generation, producer stream ID and monotonic observation sequence; sample identity is packet key plus row index |
| Source | Stable physical camera/component ID and exact role, source stream/generation/native sequence, source FrameSet/bundle key and raw artifact reference/hash when persisted |
| Image space | Source dimensions, optical frame, pixel convention and any preprocessing transform/reference; original source coordinates remain recoverable |
| Illumination | Requested emitter IDs and separate established emitter attribution/evidence; projector pattern ID/revision and projected line identity where known |
| Correlation | Exact program/step instance, acquisition evidence and requested/observed trigger references; explicit absence for imported/unavailable context |
| Time | Source timestamp/clock, host receive, SyncGroup/SyncQuality and exposure/clock mapping evidence; producer completion time is separate |
| Calibration | Exact immutable camera/rig references with schema/revision and artifact IDs/hashes where resolved; optional separately typed future laser-model reference |
| Producer provenance | Algorithm ID/version/build, canonical parameter hash/reference, exact inputs and synthetic/real/imported evidence origin |
| Quality | Packet disposition and sample flags; optional confidence/uncertainty with declared interpretation, unit and validity |

Core sample attributes are:

| Attribute | Representation / meaning |
| --- | --- |
| `org.mantis.laser.source_pixel` | f32 `[N,2]`, unit pixel; x right, y down, origin at center of original image pixel (0,0). Fractional values are representable; their availability proves no implemented subpixel algorithm |
| `org.mantis.laser.quality_flags` | u32 `[N]`; bits 0–3 mean emitter attribution unknown, line identity unknown, ambiguous identity and producer rejection respectively; unknown flag bits are preserved |
| `org.mantis.laser.emitter_index` | Optional u32 `[N]` into a bounded packet component dictionary, paired with u8 `[N]` `org.mantis.laser.emitter_valid`; omission means attribution unavailable |
| `org.mantis.laser.line_index` | Optional u32 `[N]` into a pattern-qualified line dictionary, paired with u8 `[N]` `org.mantis.laser.line_valid`; no nearest-line/index-order inference |
| `org.mantis.laser.confidence` | Optional f32 `[N]` in [0,1], paired with u8 `[N]` `org.mantis.laser.confidence_valid` and producer-defined interpretation/version; it is not a universal probability |

Dictionary entries use stable emitter IDs and pattern ID/revision plus local line
IDs. A line number is meaningful only within that dictionary; ordinal row order
is never line identity. Packet-wide known attribution can use a single dictionary
entry with all indices zero. Unknown attribution is allowed for ambiguous future
extractors and fails only consumers whose explicit requirements need known identity.
Commanded L1 cannot by itself become physically confirmed L1 attribution.
Validity masks contain only 0 (unresolved/unknown) or 1 (valid); a value column and
its mask are present together or absent together. Invalid entries use finite zero
placeholders that must not be consumed as evidence. A valid line dictionary entry
must agree with that sample's valid emitter attribution; otherwise retain line
identity as unknown. Confidence absence means unavailable, not a default score.

N is explicit and bounded by negotiated sample/payload limits. All sample arrays
share N; indices, extents, strides, finite coordinates and validity masks validate
before publication. Zero detections is a successful packet with N=0 and no sample
attributes, distinct from extractor failure or unavailable production extractor.
This respects the existing attribute validator's prohibition on zero dimensions.
Rejected/ambiguous candidates can retain flags and reasons; algorithms declare
whether they publish candidates or accepted samples. No quality threshold is
invented by the acquisition contract.

Optional namespaced attributes can carry intensity, width, sample time offsets,
uncertainty or algorithm-specific features with explicit type/shape/unit. Unknown
valid attributes survive persistence/forwarding; incompatible consumers reject
required semantics explicitly. Buffers use immutable owned views, strides and bulk
columns, never one heap-heavy object per sample. L1 implements fixed-width flag
constants and descriptor encoding in the semantic implementation contract before
L2/L6 codecs or SDK bindings expose them; it must preserve the meanings frozen
here. Schema-1 quality flags mean: emitter attribution unknown, line identity
unknown, multiple plausible identities, or producer-rejected candidate. A zero
flag word means none of these flags is set, not independently certified measurement
quality. Other quality attributes retain producer semantics.

No canonical XYZ, laser-plane solution, camera re-calibration or triangulation
lives in this packet. Future processors may create new geometry artifacts with
exact observation/calibration lineage. L6 supplies synthetic producers, validation,
round trips and typed processing inputs/outputs; a real extractor remains v0.5.

## 9. Calibration and provenance

Preserve [ADR-030](../adr/030-calibration-artifacts-revisioning-and-active-binding.md):
snapshot project-local active RigCalibration before acquisition; validate the
participating camera identities/roles/dimensions; retain the original plugin
calibration reference; stamp FrameSet/images and bundle evidence consistently
without copying pixels or looking up the database on each frame. Absence of an
active binding remains a valid raw-capture state, explicitly unavailable downstream.

New emitter/controller children do not change camera/rig artifact meanings. Their
identity/configuration/pattern revisions are provenance, **not laser geometric
calibration**. Laser/projector models belong to separate v0.5 artifacts; a future
reference must never masquerade as CameraCalibration or RigCalibration schema 1.
Resolved immutable dependencies retain artifact ID and hash as well as logical
calibration ID/schema/revision. Imported unresolved references remain explicitly
unresolved; reconstruction cannot silently use current project state to fill them.

Capture-time calibration and explicitly chosen later processing calibration are
separate provenance. Reprocessing creates a new artifact; original headers never
change. Changing activation, program or algorithm cannot reinterpret recorded
decisions or replace the historical binding.

## 10. Recording and deterministic replay

**Decision: opt-in RawCapture schema 3 for AcquisitionBundle streams.** Schema 1
and camera-only schema 2 remain unchanged/readable/writable on their existing paths.
No application-wide project/SQLite migration or old-pixel rewrite is needed.

This follows codec inspection, not the milestone number. RawCapture v2 cannot
represent a standalone trigger/control/terminal packet; `append_raw` and
finalization require exact FrameSet schema 1, whose publication forbids attributes
and non-image children. Evidence-only bundles also need nested unchanged FrameSets,
which MANTIS02 rejects. A schema-checked JSON metadata value could carry compact
per-frame facts, but cannot by itself represent a run that fails before the first
image or terminates after the last, or provide the full typed evidence stream.
A separate high-rate journal would duplicate ordering, durability and recovery
authority. Silently widening v2 would allow old readers to report image-only
success while omitting authoritative events.

L4 therefore introduces MANTIS03 for AcquisitionBundle, with an explicit bounded
member table and length-delimited typed member packets. Flat evidence/TriggerEvent/
LaserObservation packets use MANTIS01 where its typed attributes suffice;
unchanged FrameSet members use MANTIS02. Maximum nesting is outer bundle →
FrameSet → ImageFrame, not arbitrary recursion. L4 documents exact byte encoding
and compatibility fixtures before publishing a codec; no structs or bytes are
implemented by L0.

Schema 3 records use distinct `MRAWREC3` framing with the same bounded
length/checksum/complement/footer design as schema 2. Record payload limit remains
128 MiB; normal segment target remains 64 MiB. The versioned footer and packet
magic are distinct. Bundle sequence is continuous per raw artifact; child camera
counters and event sequences have their own generation semantics. Checksums cover
all evidence, headers, pixels, attributes and padding. Reuse segment sync/index,
rename-before-index recovery, mapped ownership, corruption detection and explicit
incomplete-tail handling. FNV integrity remains accidental-corruption detection,
not authentication or tamper protection.

Persist the immutable program and run configuration before ON/trigger work. Begin
the provisional raw artifact before arming; an initialization evidence-only bundle
permits failed-start diagnostics without an image. Normal stop records terminal
command/outcome evidence before sealing/finalization. Failed/cancelled runs retain
their recorded disposition; recoverable storage state does not erase a run failure.
Storage failure can prevent terminal persistence: retained diagnostics report it,
and an absent terminal event means incomplete/unknown outcome, never implied OFF.

Recovery validates each complete record, semantic order and references, rejects
corrupt complete records, and discards only incomplete trailing bytes. A process
kill can lose unpublished/in-flight evidence; power loss can also lose the active
unsynchronized segment/cache. Replay claims cover the validated recorded prefix,
not unrecorded hardware activity. Never synthesize a terminal outcome from program
intent. Recovery does not resume hardware execution.

Replay publishes the exact recorded bundle/member associations, decision order,
commands/results, unknown evidence and calibration. It never opens an executor,
re-runs emitters, sends triggers, re-pairs cameras, re-derives effective state or
substitutes active calibration. ASAP/receive-paced replay changes delivery only.
Pacing retains original clock metadata and uses a bounded wait, not a new sensor
timestamp. New algorithm processing is a distinct job/artifact, not replay.

New readers dispatch by artifact and packet/container version. Old readers must
reject schema 3 explicitly through version gating; they cannot consume its events
as schema-2 FrameSets. Exporting an image-only schema-2 derivative is an explicit
new artifact with declared omitted evidence and input lineage, never in-place
downgrade. Standalone LaserObservation artifacts use existing generic packet
storage when applicable; LaserObservation does not alone require RawCapture v3.
Compatibility promises are reader compatibility with schemas 1/2 and legacy ABI
compatibility, not old-runtime authoring/recovery support for schema-3 artifacts.
Existing v0.3 CalibrationDataset ingestion remains schema-2-only; using a bundle
capture for calibration requires a later explicit validated image-source adapter
or a declared schema-2 derivative, never silent input reinterpretation.

## 11. Plugin/device compatibility strategy

The root `MantisPluginV1`, `MantisDeviceV1`, `MantisAcquisitionV1`,
`MantisObservationV1`, `MantisFrameSetV1`, `MantisPacketV1` and `MantisProcessorV1`
stay binary/layout/meaning compatible. No appended fields, reinterpretation or
mandatory new callback in these existing tables.

The new queried `org.mantis.projected-light.v1` interface owns a selected parent
instance and its cameras/controllers as one run. Responsibilities are bounded
descriptor discovery, capability/limit reporting, program validation/preparation,
start, bounded next-bundle publication, priority abort/inhibit/OFF, stop/destroy
and structured status/evidence. It must not depend on an unrelated independently
opened MantisAcquisitionV1 handle. A plugin can expose both interfaces; explicit
requested mode determines which is used. Legacy camera-only capture continues
through v1, with no pretend laser evidence.

Reserve `org.mantis.processor.v2` for processing full immutable semantic packets,
including FrameSet/bundle inputs and LaserObservation outputs. The flat v1 adapter
currently loses composite and rich observation context; L6 must not force new
processing through it or the adapter's blanket input-header replacement.
L2 defines the new packet-view/publication responsibility shared by these queried
interfaces; L6 implements the processing adapter and synthetic producer.

L2 writes C-only tables with fixed-width fields, opaque instance/buffer handles,
struct_size/abi_version, explicit field presence, borrowed synchronous descriptor
callbacks and retain/release ownership. C++ wrappers remain above them. Next calls
have finite deadlines; abort is the explicitly thread-safe side path that can
inhibit/OFF while next is pending, without unload/destroy racing a callback.
Executor emergency behavior must not rely on callback completion. Allocation,
exception containment, malformed-output validation and optional-interface queries
retain current SDK rules. Unknown queried interfaces return null; absence disables
only projected-light support. Old v0.1/v0.2 DSOs must still load and capture.

Exact C layouts, integer constants and packet-view serialization are implementation
details to specify/test in L2, not speculative ABI code in L0. Additive interface
versions have ABI version 1 root compatibility; interface `.v2` is not a root ABI
bump. Isolated device streaming remains deferred; existing in-process device
limitations must remain explicit, and a future bridge can implement these same
semantics without changing its yet-unfrozen wire protocol.

## 12. Daemon control plane, data plane and X1 partition

DeviceService exposes capability/limit discovery. CaptureService owns program
validation/start/stop/status and run authority. Artifact/Job services own immutable
program/evidence publication, finalization, replay and recovery. DiagnosticsService
exposes compact failure/health summaries. No new client-owned hardware service or
scanner singleton is introduced.

L5 adds compact typed DTOs for participants, program/reference, validation results,
execution mode, requested evidence level, run state/step, commanded and available
acknowledged/effective summary, finite limits, queue health, structured errors and
OFF/inhibit outcomes. Start creates run identity before hardware work; failed start
remains inspectable even if no frame exists. Idempotent stop/OFF does not restart
or re-trigger; request retries use scoped request identity to avoid duplicate runs.
Unknown/late generation commands are rejected. Protocol v1 keeps existing field
numbers and the 4 MiB bound; a large program is an artifact/data reference, not an
unbounded inline control payload. SDK/CLI/Studio use the same daemon semantics.

Large arrays, FrameSets, complete high-rate evidence and LaserObservation samples
stay on the explicit data plane (ADR-007). Control returns immutable references
and bounded summaries; ordinary Protobuf events never carry measurement buffers.
The current local mapped-file/leased preview transport remains usable after an
explicit format-version upgrade. Bundle preview projects its FrameSet with lineage;
preview absence on an evidence-only bundle is valid. No UI processing is required
on the authoritative recording path.

Normal X1 topology remains Q6A `mantisd` + hardware ownership + acquisition/program
executor + future source-proximal extractor, with triangulation/reconstruction on
host/worker by default. X1 Pro may place both sides locally using the same typed
DAG. USB, network/Wi-Fi and local IPC carry identical semantics. L6 proves the
observation boundary with local/synthetic streams; it does not implement the
complete authenticated remote data plane or ADR-032 worker scheduling.

## 13. Boundedness, backpressure and observability

All limits are positive finite validated values, advertised by the executor/runtime,
reserved before start and recorded with the program/run. No zero-as-unlimited
convention. Hardware-specific timing ceilings require measured L7 evidence.

| Resource | Required bound / failure behavior |
| --- | --- |
| Ordinary commands | Fixed capacity and byte budget; busy before dispatch; deadlines and maximum event responses; separate OFF/inhibit path |
| Programs | 256 declared / 1,000,000 executed steps maximum, smaller executor limits allowed; finite total/step/ON durations and checked repetition expansion |
| Hardware execution | Finite submitted and pending command count; cancellable/inhibitable generation; no unbounded FIFO or retries |
| In-flight capture/evidence | Explicit frame/event/byte/window bounds; reserve before trigger; timeout/failure for unresolved required association |
| Bundle | At most 64 members, at most one FrameSet/16 images, 128 MiB serialized record limit; bounded tables/strings/attributes |
| Measurement recorder | LOSSLESS with finite count and byte limits and finite saturation deadline; OFF/inhibit and fail if unsustainable; no silent discard |
| Preview / diagnostic display | Independent explicit LATEST_ONLY/lossy policy, counts and stale status; never authorizes loss on measurement path |
| Replay | One bounded segment index at a time, finite retained mappings/consumer window, bounded pacing waits, cancellation between records; no whole-capture population |
| Diagnostics | Bounded snapshot/event/string history; authoritative acquisition events remain recorded. Rate-limited text/optional telemetry carries suppressed counts; log storage uses an explicit finite retention policy |
| Clients / downstream | Finite leases, retention and buffering; disconnection cannot create unbounded pinned buffers or transfer hardware ownership |

The current 32-record / 50 ms writer and capacity-one preview are the inherited
camera baseline, not evidence of projected-light throughput. L3/L4 add byte
reservation and evidence accounting, preserve the old mode, and record their
chosen capacities. Smaller safe hardware queue limits can reduce concurrency.
Runtime may pause **before** the next step only where the validated executor
supports it and OFF/ON-duration constraints are satisfied. A started exposure
cannot be silently discarded because storage is slow. Stop/abort latency cannot
depend on recorder or downstream progress.

Collect commanded/acknowledged/observed event counts, trigger/camera association
failures, unavailable evidence counts, ON/OFF request/outcome, native gaps, exclusions,
produced/committed bundles, byte/queue high-water/saturation, late/stale events,
step/abort latency, copies/allocations and storage throughput. Preserve root cause
plus cleanup errors. Critical state-transition/evidence overflow fails explicitly;
it is not merely a lossy diagnostic. ARM64 portability, allocation/ownership and
measured performance follow ADR-033; no throughput or optical timing claim is
inferred from requested FPS.

## 14. Hardware integration boundary and facts required for L7

The inspected X1 backend/profile provide camera media/V4L2 setup, native modes,
timestamps and initial controls. They contain **no authoritative selection** of
Linux GPIO, serial/I2C/SPI, RP2040, MSPM0, ESP or another laser controller.
Those technologies must not enter generic contracts. The executor boundary
accepts validated finite operations and returns capability-scoped evidence.

The following X1 facts are deliberately **unknown** and must be supplied and
reviewed before L7 physical enablement:

| Required fact | Needed evidence |
| --- | --- |
| Controller topology/ownership | Actual components, which controller drives each emitter/camera, and resource exclusivity |
| Electrical/protocol interface | Pinout/channel mapping or protocol/version, voltage/current limits, isolation/level conversion and error/reset behavior |
| L1/L7 control semantics | Enable versus power/modulation/pulse controls, active polarity, valid combinations and mutual-exclusion rules |
| Startup/reset/disconnect state | Physical output state at boot, reset, power/transport loss and controller initialization; not software defaults |
| Timing limits | Settling, hold, maximum ON duration/duty cycle, command/abort latency, resolution/jitter and tolerated rate |
| Pulse semantics | Edge polarity, width/minimum spacing, pulse count behavior and how pending pulses are cancelled/inhibited |
| Camera trigger mode | OV9281/board wiring, actual supported driver/sensor trigger configuration, readiness, exposure/readout relation and native-counter association |
| Acknowledgement/readback | Acceptance/completion versus actual pin/optical sensing, coverage/latency and unavailable evidence |
| Clock/trigger evidence | Native trigger identity/generation, clock semantics/mappings, camera exposure association and measurable timing uncertainty |
| Independent safety mechanisms | Interlock/watchdog/fail-OFF implementation, timeout/reset behavior, independence from daemon/software and physical test procedure |
| Optical validation | Instruments/method for emitter activity and exposure overlap/skew; scope of claims the evidence can support |

Camera mode hardware acceptance remains [the Q6A acquisition record](../hardware/x1-q6a-acquisition-validation.md).
Existing v0.3 M8 [camera-only calibration acceptance](../hardware/x1-geometric-calibration-validation.md)
is still pending and must not be claimed complete by laser integration. L7 may
progress with a fake executor while these facts are unavailable, but physical
operation/acceptance cannot be declared. No invented controller or timing numbers
fill this table.

## 15. Implementation package map and validation philosophy

| Package | Implements / review gate |
| --- | --- |
| L0 — Architecture & Contract Freeze | This baseline and ADRs 040–043, roadmap/status consistency; documentation only |
| L1 — Canonical Laser Semantics | Pure schema/domain program, evidence, TriggerEvent and LaserObservation models, typed state/identity/time/presence rules and validators; concrete field/flag encoding under this baseline; no extractor or hardware code |
| L2 — Device & Plugin Contracts | Additive queried tables/SDK adapters, component capability descriptors, generic camera participant selection, ownership and deadline/abort contract; frozen legacy DSOs still load; no X1 electrical assumptions |
| L3 — Deterministic Sequencer | Daemon runtime program validation/reservation/state machine and fake executor; causal event correlation, priority OFF, finite queues/deadlines and fault behavior; no line extraction |
| L4 — Evidence, Raw Recording & Replay | Opt-in bundle codec/RawCapture schema 3, program/config provenance, evidence-only startup/terminal records, version gating, recovery and exact hardware-free replay; preserve schema 1/2 bytes and pairing |
| L5 — mantisd Control Surface | Compact additive service/protocol/SDK/CLI controls, inspectable failed starts, idempotent stop, events and data references; no high-rate Protobuf payloads |
| L6 — LaserObservation Boundary | Full-packet processing adapter, synthetic/test producer, typed DAG/bulk buffers, artifact round trips and local semantic stream verification; production image algorithms remain v0.5 |
| L7 — X1 Hardware Integration | Select/implement plugin-private executor only after factual hardware review; validate controller/camera mode and independent fail-OFF; preserve accepted free-running profile |
| L8 — Reliability & Physical Acceptance | Fault/recovery/backpressure/cancellation/teardown/transport tests, x86_64 and native ARM64 compatibility, measured latency/throughput/soak and real timing/state evidence; no scanner-mm accuracy or certification claim |

L2 consumes L1 semantics; L3 consumes L1/L2; L4 consumes their publication model;
L5 consumes L3/L4; L6 consumes L1/L2/L4 processing/storage boundaries. L7 needs the
validated L3–L5 path and reviewed hardware facts. L8 validates the integrated
contracts. Each package records concrete implementation contracts and tests before
declaring its boundary implemented; semantic changes to L0 require an explicit ADR
amendment, not invention within an implementation commit.

Use pure validation and deterministic fake-executor tests for program bounds,
state transitions, command/ack/effective separation, late/duplicate/reset events,
missing evidence, zero samples and column validation. Contract tests prove legacy
ABI loading, C compilation, callback/buffer lifetime and frontend/core boundaries.
Storage tests cover old and new golden formats, two-pass exact replay including
unknown evidence/calibration, corrupt complete records, incomplete tails and
failure before first/after last image. Replay tests deny access to hardware and
change active calibration to prove neither is consulted.

Fault tests exercise camera/controller/sequencer/recorder errors, queue exhaustion,
disk full, client loss, required downstream loss, cancellation/shutdown races and
plugin/process termination. Measure OFF request latency separately from observed
physical OFF. Real L7/L8 evidence must identify hardware/software versions, program,
capabilities, calibration, instruments, clocks, measurement method and uncertainty.
Fixtures establish software behavior only. Hard timing/physical exposure claims
require corresponding physical measurements; missing measurements remain unavailable.
No arbitrary optical acceptance thresholds are frozen before evidence review.

## 16. Deferred work and L0 acceptance review

Deferred: all v0.5 algorithms/laser geometry/triangulation; v0.6+ reconstruction;
complete network data plane, bridge wire implementation and worker scheduling;
DMABUF/external-buffer ownership; infinite/adaptive programs; automatic re-arm,
transparent reconnect or safety certification. Camera/rig calibration mathematics
and the accepted 5 ms correspondence mode remain outside this change.

L0 review should confirm the opt-in schema-3 justification, typed evidence/presence
and exposure-effective requirements, finite execution/abort authority, additive ABI
responsibilities, unchanged historical contracts and the hardware facts needed
before L7. Exact C/wire layouts and physical timing limits are deliberately later
specifications under these frozen semantic decisions. L0 acceptance does not imply
L1 implementation, v0.3 M8 acceptance or any real laser acquisition result.
