# When could a CI job be omitted?

**Proposal only — NOT ACTIVATED.** For [Issue #110, scope 6](https://github.com/martinkoenig/mantis-studio/issues/110). Today the answer is **never on the strength of the shadow decision**: FULL is unconditional, `execution_authorized=false`, `closure_complete=false`. This is not an ADR, a ruleset, a local-final qualification change or approval to implement a selector. It adds no check. The [collector reference](ci-shadow.md) describes what actually runs.

## What a future decision would have to explain

Start with the **full applicable set**, not with an empty list to fill from changed folders. Freeze the trusted policy/workflow revision, event, base/head commits and trees, tested checkout and parents, diff digest, completeness, status and both sides of each changed path. Pin inventory and configured producer inputs by source, toolchain, build mode, architecture and digest. Traverse changed input → generated/source target → reverse consumers → test, fixture and job. Record observed, inferred and unresolved edges separately. Use stable IDs and deterministic ordering. Keep private paths and raw diagnostics out of the public projection; retain reviewable evidence separately.

For each test/suite and platform record mode (feedback or final), domain, tier, highest applicable risk, edge provenance, **why included or why demonstrably unaffected**, and unknown/error reasons. An omission would require affirmative evidence for that candidate, not a label, a directory prefix, or the lack of a graph hit. Union all domains before deciding. Missing inventory, conflicting labels, parser failure, unsupported status, unknown consumer or evidence/version drift means FULL; if FULL cannot be verified, hold rather than pass.

## Optional aggregate: evidence first, status second

A possible stable context name is `CI integrity` (proposed, **does not exist here**). Initially it would report alongside the full jobs, without being required. Its trusted definition would run on every applicable event, without path filters, even after a dependency fails. It would compare an independently derived expected set to provider run/job identities and execution evidence, **not** count green names or trust an in-PR manifest. A mandatory check may not omit itself. If an explicitly approved future policy ever permitted omission, distinguish “not required for this decision” with its reviewed proof from “ran and passed”; that exception could never satisfy a still-required or full-integrity job.

Bind repository, workflow revision, producer app, event/ref, candidate, tested tree/SHA, run and attempt per job. For PRs bind base and PR head to the tested merge's ordered parents; do not compare only the head ref. Fork code and its artifacts remain untrusted: read-only PR evaluation, no secrets, writes, privileged checkout/execution or trusted cache publication. Recompute expectations from trusted inputs. For protected pushes bind the actual `before` and resulting SHA, not a prior PR run or an assumed first parent. A manual observation is unsupported/FULL, not proof for either event.

| Evidence presented (paper dry-run) | Expected aggregate result |
|---|---|
| Every applicable job actually executed its obligations successfully for the matched identity | Success only for that event/decision. Record what ran and any separately authorized non-applicability. No release or merge authority. |
| Job missing, queued or pending, including a filtered-out required workflow | Not ready; wait only until a bounded deadline, then fail/hold with missing identities. If the aggregate itself never reports, protection must still block. |
| Failed, timed out, cancelled/superseded, skipped, neutral, unknown conclusion, or green wrapper around skipped required steps | Not success. Report the exact job/step and cause or unknown; require actual coverage on the current identity. Never substitute an older successful attempt for the failed one. |
| Five protected checks green but ARM artifact absent; duplicate name from another app; fork reports green on head, not tested merge | Reject incomplete or mismatched evidence. Neither a name collision nor an artifact assertion can satisfy the missing execution. |
| Configured-toolchain absent on a develop push vs. absent on a PR | Source-defined non-applicability on push, missing obligation on PR. Never copy a PR success into the push set or wait for a push job the workflow cannot emit. |

## Evidence to change the answer, and how to restore FULL

1. **Compare before omitting.** Keep every full run. Freeze each hypothetical plan *before* examining results. Pair it with actual same-input full outcomes, separating historical adjudicated source/test failures, infrastructure or unknown causes, controlled seeds and caller assertions. Sample across domains, risk, platforms, mixed changes and failures rather than only recent greens. Compare predicted tests with independently labelled necessary tests per profile: report missed necessary tests (false negatives), recall and precision with denominators and unknown/unlabelled counts. No labels means unknown, not 100%. Require independently chosen missing-edge seeds to produce the intended miss and exact restoration; investigate every miss, never average away an R1 miss. Estimate runner minutes separately from measured end-to-end time and local queue/service costs; no speedup is established here.
2. **Keep a full comparison after any future change.** Run an unfiltered full matrix on scheduled pinned revisions, at integration/release cuts before proceeding, and on each actual protected postmerge SHA. Include configured-toolchain via its supported manual/full equivalent at cuts, not as a fictional push context. Compare actual failures with frozen plans; retain run/attempt, exact inputs, logs and mismatches. An unqualified resulting SHA stays unqualified. A nightly green cannot repair a missing PR check or authorize release.
3. **Dry-run the transition with the original checks intact.** Before any activation, independent source/test and design review would have to qualify closure, historical/seeded recall, trusted provenance and feedback boundaries. The repository owner would have to approve the exact eligible scope, evidence thresholds, full-run cadence, timeout, rollback owner and any deliberate binding-doc or ruleset change. Rehearse names, app bindings, triggers, stale base, fork, cancellation, rename and absent-context behavior without changing live requirements. Exercise both old and proposed reporting paths side by side on real events, including deliberate missing coverage.

   Before any approved switch, record the old and proposed context/app bindings and confirm the new reporter exists on current open PRs. Require it **alongside** the old checks while all still run; verify missing work blocks. Only an explicit owner decision could then replace specific bindings and permit named omissions. Do not stop emitting a context while a rule still requires it. Paper examples are not that rehearsal.
4. **Rollback order matters.** On a miss, stale policy, missing report, workflow/ruleset drift or integrity failure, stop selective admission and hold affected merges/cuts. Restore unconditional full execution first; keep every currently required context reporting truthfully, including the aggregate if ever required. Requalify affected candidates and resulting revisions on their actual identities, preserving failures. Verify the original named full jobs are present, actually ran and are app-bound before an authorized owner restores/verifies the original requirements. Only then retire a replacement context. Never delete a required reporter first, synthesize a green skipped job, bypass protection or treat rollback as proof for an earlier gap.
